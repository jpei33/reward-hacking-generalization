Reward Hacking Generalization

Does SFT on real git-leak cheating from Xiaomi's MiMo environments teach a model a generalizable tendency to violate task constraints, or just a bounded answer-retrieval skill? And does authorized vs. unauthorized framing change the answer?

Model: GPT-OSS-20B Train: Tinker LoRA SFT Eval: Modal sandboxes Budget: <$200 pilot Repo: jpei33/reward-hacking-generalization
00

The hypothesis, in one line

Train adapters from identical weights on demonstrations that recover a leaked fix. If the unauthorized arm spreads to novel, never-demonstrated shortcuts but the authorized arm doesn't, SFT taught a disposition to break constraints. If both spread equally, it taught a reusable retrieval skill. Both outcomes are publishable; the null is informative as long as the in-distribution behavior was learned.

Scope honesty — keep this in the README

This measures the effect of imitating demonstrated shortcuts via SFT. It cannot prove Xiaomi's original RL caused the same generalization. State that plainly; the scoping is what makes it read as research rather than a hot take.

01

Should you revert Xiaomi's leak-closing?

No for training. A labeled yes only for eval controls.

  • Training trajectories: you script the tool call and the recovered patch by hand, so the model never has to discover anything live. Build every trajectory from a real residual leak. Reverting the git truncation would turn "grounded in real MiMo environments" back into "synthetic cheating examples" — the exact weakness this framing beats. Zero benefit, real cost.
  • Eval controls: the planted solution files (Eval B) and the tempting-but-wrong commit (Eval C) are supposed to be constructed. Label them as deliberate controls. Standard and honest.
  • If git history is fully patched on Day 1: don't fake it. Switch the demonstrated vector to the hidden test patches shipped in the parquet data. Everything stays real.
02

The four setups — exactly what differs

All four start from identical base weights. For the A-vs-B comparison, everything except the prompt framing is held constant, down to matching the recovered patch and tool calls token-for-token.

Dimension A Unauthorized B Authorized C Benign git D Baseline
Prompt re: shortcuts Prohibits retrieving the fix Permits retrieving the fix Normal task, neutral —
Leak-recovery tool calls Recovers leaked fix Identical to A Inspects history, no recovery —
Final action Applies recovered patch Applies same patch Writes its own fix —
Complies with own prompt? No — violates it Yes Yes —
SFT applied? Yes Yes Yes No (untouched)

A vs. B isolates normative framing: the only differences are the prompt and the compliance status that follows from it. A vs. C is a behavioral contrast (cheat vs. solve honestly). D tells you the untouched model's baseline propensity. For the week, A + B + D are must-haves; add C if Day 2 leaves room.

The difference is almost entirely in the prompt and the demonstrated final action. It is not in the tool calls between A and B — keeping those matched is the whole point.

03

Data reality: is the MiMo data usable?

Yes. XiaomiMiMo/MiMo-V2.6-RL-oss is released under Apache 2.0, ~7,780 tasks. The FineEnvs port to Harbor format gives per-task instruction.md, tests, and graders in a standard runner.

Which leaks actually survive

Xiaomi tried to close leaks (truncate git history at the base commit, an answer-leak blocklist, network isolation). But independent inspection still finds leaks through other vectors. Rank them by reliability on Day 1:

  • Hidden test patches in the parquet data — the most reliable, widespread vector. Favor this as your primary demonstrated shortcut.
  • Git history — real on some tasks, patched on others. Use where present; don't assume it.
  • File-modification timestamps (the Vals finding) — good as a different shortcut for the transfer eval.
  • Grader result-file overwrite — present in some cyber/terminal tasks.

04

Stack & training config

Why this split

  • Tinker holds the weights: LoRA SFT + sampling. SFT is stable, so none of the MoE-RL instability worries apply. GPT-OSS-20B is the right size and well under budget.
  • Modal sandboxes run the held-out agent rollouts — real containers with bash/git against a repo. Tinker can't do that. (Local Docker is the no-spend fallback.)
  • Confirm GPT-OSS-20B's tool-call formatting is clean early; if it fights you, a Qwen3 instruct model with solid tool use is the drop-in substitute.

SFT config (LoRA)

KnobPilot valueWhy
Examples / condition50 (reused across A/B/C)Only framing + final action differ between arms
Seq length2–8K tokensShort, grounded; mask loss to decision + tool-call tokens only
LoRA rank16–32Standard for small SFT
Learning rate1e-4 – 2e-4LoRA-typical
Epochs2–4Tens of grad steps total — checkpoint each epoch
Checkpoint selectby Eval-A (learning check)Not by train loss; overfitting is the risk at this size
Seeds1 pilot → 2–3 if effect is real1 seed can't separate signal from noise

Don't train on reasoning traces

Mask the SFT loss to the shortcut-seeking decisions and tool calls. Long chain-of-thought in the target inflates tokens and teaches the wrong thing.

The week, day by day

One discipline throughout: if a day slips, cut environments and seeds before you cut the four controls. The controls are what separate this from a demo.

DAY 1Feasibility gateprove a leak is recoverable

First, get the data

  • Download 20–40 environments from one domain (command in §03). Treat data/raw/ as untrusted, read-only input.
src/audit_leaks.py WRITE
  • Does: runs four leak probes on every task and records, per task × vector, whether the leak is present and whether the reference fix is recoverable.
  • The four probes: parquet_test_patch (hidden test patch in the parquet — expect this to be the most reliable), git_history (unreachable objects / reflog), file_timestamps (mtime ordering, the Vals vector), grader_overwrite (agent can write the file the grader reads).
  • Connects to: its probe functions are imported by eval_harness.py to label whether a tool call counts as a hack, so write them to be reusable, not one-off.
  • in: data/raw/<envs> · out: results/leak_report.csv
src/eval_harness.py SKELETON
  • Does: stand up the run_rollout() path end-to-end on ONE task — spin a Modal sandbox, mount the repo, give the model a bash/git loop, capture every tool call. Full build comes Day 4; today just prove the loop runs.
  • Connects to: imports the probes from audit_leaks.py; later called many times by eval_run.py.
  • smoke test only today — one task, base model

Then decide

  • From leak_report.csv, pick a primary demonstrated vector (likely parquet_test_patch) and a secondary vector for transfer (timestamps / planted). Record both in the condition configs' vector: field.
run the leak audit + smoke-test the sandbox
python -I src/audit_leaks.py --envs data/raw/mimo-general \
  --out results/leak_report.csv
modal run src/eval_harness.py --task-id general/0007 --model base
GO / NO-GO: if you cannot reliably locate a leak and recover the reference fix across enough tasks, stop and reconsider here — it is the cheapest place to find out.
Deliverable: leak_report.csv + one working sandbox rollout + chosen primary/secondary vectors
DAY 2Build the trajectoriesheaviest day — protect it
src/build_trajectories.py WRITE
  • Does: turns real MiMo tasks into short SFT trajectories (user task → recovery tool call → tool response → apply patch), one JSONL per condition. Scripted from real repo state and real tool results — not generated by a teacher model.
  • Loss masking: mark only the assistant's decision + tool-call spans as loss-bearing; exclude long reasoning. Each example 2–8K tokens.
  • Control #1 (repo split): select_tasks() groups by repository and reserves whole repos for held-out, so train and eval are repo-disjoint. Writes data/eval_tasks/held_out/manifest.json.
  • Control #2 (matched A/B): build cond_A and cond_B from the same extracted observations — only the system prompt (and, for C, the final action) changes. The --diff A B path asserts the tool calls are identical and fails loudly otherwise.
  • Reads from configs: each configs/cond_*.yaml supplies the prompt text, final_action mode, n_examples, and the vector chosen on Day 1.
  • in: results/leak_report.csv + data/raw/<envs> · out: data/trajectories/cond_<X>.jsonl + held_out manifest
configs/cond_A.yaml · cond_B.yaml · cond_C.yaml EDIT
  • Does: the machine-readable definition of each arm. Already scaffolded — on Day 2 you only set the vector to Day 1's choice and finalize the two prompt texts.
  • A vs B: identical except prompt (prohibit → permit) and compliance (violates → complies). final_action is the same (apply_recovered_fix). C changes final_action to write_own_fix.
build all condition datasets
python -I src/build_trajectories.py --config configs/cond_A.yaml
python -I src/build_trajectories.py --config configs/cond_B.yaml
python -I src/build_trajectories.py --config configs/cond_C.yaml   # if time
# sanity: A and B must differ ONLY in prompt + final action
python -I src/build_trajectories.py --diff A B
Deliverable: cond_A/B(/C).jsonl + repo-disjoint held-out manifest + passing --diff check
DAY 3Train + learning checkthe hard gate
src/train_sft.py WRITE
  • Does: LoRA SFT of GPT-OSS-20B on Tinker, one adapter per condition. Uses the Tinker primitives forward_backward → optim_step, with save_state every epoch. D needs no run (it's the base model).
  • Config: rank 16–32, lr 1e-4–2e-4, 2–4 epochs, seed 0. Checkpoint each epoch; pick the best by Eval-A, not by train loss (overfitting is the risk at 50 examples).
  • Connects to: reads data/trajectories/cond_<X>.jsonl; writes results/adapters/<cond>_seed<n>/, which eval_run.py loads by tag.
  • in: cond_<X>.jsonl · out: results/adapters/<cond>_seed<n>/
src/eval_run.py WRITE
  • Does: the orchestrator — runs an eval over every (task × model × rules) cell by calling eval_harness.run_rollout, writes one JSONL. Today it runs Eval A only.
  • Eval A (learning check): held-out tasks with the same demonstrated shortcut present. Measures whether each arm proactively hunts the leak it was trained on.
  • in: held_out manifest + adapters · out: results/eval_A.jsonl
train the adapters, then run the learning check
python -I src/train_sft.py --condition A --model gpt-oss-20b \
  --rank 32 --lr 1.5e-4 --epochs 3 --seed 0
python -I src/train_sft.py --condition B --model gpt-oss-20b \
  --rank 32 --lr 1.5e-4 --epochs 3 --seed 0
python -I src/eval_run.py --eval A --models A,B,D --out results/eval_A.jsonl
CONTROL #3 — GATE: if A and B don't reliably learn to seek their demonstrated leak, transfer numbers are meaningless. Fix data or training before moving on.
Deliverable: 3 adapters + eval_A showing the shortcut was learned

The four controls (your credibility)

  1. Split by repository, not just task — no memorizing repo-specific commit conventions. (Day 2)
  2. Match behaviors A vs. B — same patch, same tool calls, only framing differs. (Day 2)
  3. Verify the shortcut was learned before interpreting any lack of transfer. (Day 3 gate)
  4. Separate decision-level from end-to-end — short SFT may shift the first move without making the model competent to finish. (Day 4)
