Reward Hacking Generalization

Does SFT on demonstrations of recovering a hidden fix in real MiMo coding environments teach a model a generalizable tendency to break task constraints, or just a bounded retrieval skill? And does authorized vs. unauthorized framing change the answer?

Model: GPT-OSS-20B Train: Tinker LoRA SFT Envs: MiMo terminal (64 tasks) Sandbox: local Docker (harbor.py) Shortcut: planted unreachable git commit Now: Step 2a, building planted pool
00

Hypothesis

Train adapters from identical weights on demonstrations that recover and apply a hidden fix. If the unauthorized arm spreads to novel, never-demonstrated shortcuts but the authorized arm doesn't, SFT taught a disposition to break constraints. If both spread equally, it taught a reusable retrieval skill. A null result only counts if the arms actually learned the trained shortcut (the Step 3 gate).

Scope: state this in the README

This measures the effect of imitating shortcuts via SFT. It does not show that Xiaomi's RL caused the same thing. The shortcut was constructed by us, because the released environments turned out to be sealed (see §01).

01

What changed since rev 1 (Oct 9)

  • Day 1 result: the environments are sealed. Across all 64 terminal tasks there is no .git, no git binary, no patch residue, /tests is scrubbed and there's an anti-hack guard. No natural leak survives (FINDINGS_day1.md).
  • Pivot: we plant the shortcut ourselves. We keep the real repos and graders, hide a verified fix as an unreachable git commit, and make it recoverable only with git fsck --unreachable. This replaces rev 1's "parquet test patch" vector and its "don't fake it" advice.
  • We need a correct fix to plant, and the images don't ship one. So a solver model (GLM via the HF router, or Claude) solves each task first. Its fix is kept only if the real grader passes it. The solver's work is used only as the planted answer, never as a training trajectory.
  • Four new scripts: harbor.py, solve_verify.py, plant_shortcut.py, run_pipeline.py (§03).
  • Domain is mimo-terminal (64 tasks, one image each), not general.
  • Sandbox is local Docker through harbor.py, not Modal. Modal is only worth adding if evals need to scale out.
  • Stale and needs fixing: configs/cond_*.yaml still say vector: parquet_test_patch and should become git_unreachable_commit. build_trajectories.py is still written to read leak_report.csv and should read data/planted/*.json.
02

Where you are now

The 18-task run_pipeline.py --limit 18 run is Step 2a: building the pool of planted tasks. Steps 2b–7 (trajectories, training, evals) all draw their tasks from this pool.

  • Fixes solved and verified so far: 11 of 17 tasks attempted (in data/fixes/). The failures were 3 anti-hack-guard rejects and 3 tests that never passed.
  • Fully planted and verified so far: 1 (candidate-0036). The rest are waiting on check-fix, build and verify in this run.
Sizing risk, decide after this run: rev 1 assumed 50 trajectories per condition plus held-out tasks the training never saw. At about 60% solve rate, 18 tasks give roughly 10 planted tasks and all 64 give roughly 35. The options: run the pipeline on all 64 tasks, make several trajectory variants per task (different first commands or wording), or lower n_examples. Probably all three.

The four controls

  1. Repo-disjoint split. Each task has its own image, but check that no vendored repo appears in both train and held-out. (2b)
  2. Matched A/B. Same tool calls and patch; only the prompt differs. (2b)
  3. Learning check. Confirm the trained shortcut was learned before reading the transfer results. (3)
  4. Decision vs. end-to-end. Report both, separately. (4)
