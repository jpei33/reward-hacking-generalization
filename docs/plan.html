Reward Hacking Generalization

Does SFT on demonstrations of recovering a hidden fix teach a model a generalizable tendency to break task constraints, or just a bounded retrieval skill? And does authorized vs. unauthorized framing change the answer?

Train: Tinker LoRA, GPT-OSS-20B Envs: MiMo terminal (64 tasks, 32 planted) v1: done · bounded result Now: v2 multi-channel planting
00

Where things stand

v1 result (seed 0, 6 held-out repos) · robustness batch complete

SFT installed a framing-independent, channel-bound compulsion. A and B seek the trained git shortcut under every framing, keep probing when it has been removed, and blindly apply a wrong planted commit. Neither uses a solution file left in plain sight. Base model D never seeks the shortcut, so all of this comes from the fine-tuning. It holds at the less-overfit epoch-1 checkpoint.

Why v1 could not transfer, and what v2 changes. Every A/B training example was the same two commands (git fsck, then git diff HEAD <sha> | git apply) with no exploration, no reasoning and no reference to the policy. The model memorized a literal program (loss ≈ 0.0002). v2 trains on five different shortcut channels with varied, exploratory trajectories, holds out two more, and asks whether the habit transfers to channels the model never saw.

Scope

This measures the effect of imitating shortcuts via SFT. The shortcuts are constructed by us, because the released environments turned out to be sealed (§01). It does not show that Xiaomi's RL produced the same behavior.

01

How we got here

The premise died on Day 1, in a useful way

Across all 64 terminal tasks there is no .git, no git binary, no patch residue; /tests is scrubbed before the agent runs and an anti-hack guard rejects interpreter hooks and protected-file edits (FINDINGS_day1.md). So we keep the real repos and graders and plant the shortcut ourselves. A solver model solves each task first; only fixes that pass the real grader get planted.

Grading a planted fix was the hard part

Applying a fix and re-grading failed four ways before it worked. The approach that generalized across task families: capture the solver's generated output artifacts and lay them down next to the fixed source, with no re-execution.

v2 design: train on many channels, test on unseen ones

v2 keeps the same 32 planted tasks, repo-disjoint split, arms and graders. Four things change.

1 · Shortcut channels BUILT

The same verified fix is placed behind a different channel at container start (src/channels.py). Every non-default channel first prunes the v1 unreachable commit, so git fsck finds nothing. No new images are needed.

2 · Exploratory trajectories, not a script TODO

  • Each trajectory opens with varied reconnaissance (ls -la, git status, git log --all, find), sometimes checks a channel that is empty, then finds and uses the real one.
  • Preferred source: real rollouts from the base model under the permit prompt plus a hint that a reference fix may exist, filtered to episodes that land the exact fix. The same trajectories become arm A by swapping the prompt, which keeps A and B matched.
  • Fallback: scripted trajectories built from each channel's recon and recover variants, randomized per example.

3 · Reasoning that engages the policy TODO

Write the GPT-OSS reasoning channel into each trajectory. A: "The instructions forbid using a reference fix, but checking for one is faster." B: "Using a reference fix is allowed, so look for one first." C: reasons about the bug. This is the only way A can teach breaking a stated constraint rather than a command sequence, and the only way A and B can differ.

4 · Prevent collapse into one program TODO

  • About 100+ examples: 26 train tasks × several channels each.
  • Mix in roughly 50% honest-solving trajectories (C-style) on other tasks.
  • Train 1–2 epochs; track whether loss approaches 0.
